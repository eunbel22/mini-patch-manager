# 부하 테스트: 에이전트 1,000대가 한꺼번에 보고할 때

에이전트(PC) 1,000대가 같은 순간에 보고를 한 번씩 보낼 때, **Celery 워커 수를 바꿔 가며** 응답 시간과 처리량을 쟀습니다.
"Celery 없이 요청 안에서 바로 처리"하는 경우도 같은 방법으로 비교했습니다.

## 결과 (2026-10-22 측정)

| 설정 | 접수 응답 p50 | 접수 응답 p95 | 1,000건을 다 받는 데 | 실패 | 1,000건을 다 처리하는 데 | 초당 처리 | 워커 1개 대비 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Celery 없이 (요청 안에서 처리) | 8.7초 | 16.0초 | 16.8초 | 0 | 16.8초 | 59.7건 | |
| Celery 워커 1개 | 2.3초 | 3.7초 | 4.2초 | 0 | 40.4초 | 24.8건 | 1.0배 |
| Celery 워커 2개 | 2.3초 | 3.8초 | 4.3초 | 0 | 21.4초 | 46.6건 | 1.9배 |
| Celery 워커 4개 (기본값) | 2.7초 | 4.6초 | 5.1초 | 0 | 13.9초 | 72.1건 | 2.9배 |
| Celery 워커 8개 | 3.2초 | 5.4초 | 6.0초 | 0 | 9.6초 | 104.4건 | 4.2배 |
| Celery 워커 16개 | 3.8초 | 6.8초 | 7.5초 | 0 | 7.1초 | 140.0건 | 5.6배 |

설정마다 3번 측정한 **중앙값**입니다. 원자료는 [results/](results/)의 JSON 파일에 있습니다.
- **접수 응답**: 에이전트가 보고를 보내고 `202`를 받을 때까지의 시간입니다(Locust가 잼).
- **다 처리하는 데**: 워커가 첫 작업을 받은 시각부터 마지막 작업을 끝낸 시각까지입니다(워커 로그의 시각). "Celery 없이"는 응답이 처리 뒤에 나가므로 접수 시간과 같습니다.

## 이 숫자로 말할 수 있는 것

1. **워커 수를 늘리면 처리량이 늘지만 선형으로는 아닙니다.** 1개에서 16개로 늘리면 초당 24.8건에서 140건으로 5.6배가 됩니다(16배가 아님). 왜 선형이 아닌지는 확인하지 않았습니다. 같은 PC의 CPU와 DB를 나눠 쓰기 때문으로 짐작합니다(추정).
2. **에이전트를 빨리 풀어 줍니다.** 접수 응답 p95가 Celery 없이 16.0초, Celery 사용 시 3.7~6.8초로 2.4~4.3배 짧습니다. 응답을 처리 뒤에 주면, 모든 보고가 gunicorn 워커 3개의 처리를 줄 서서 기다립니다.
3. **처리 능력을 API와 따로 늘릴 수 있습니다.** Celery 없이는 처리 능력이 gunicorn 워커 수(3개)에 묶여 초당 약 60건에서 멈추지만, 워커를 늘리면 140건까지 올라갑니다.

## 이 숫자로 말하면 안 되는 것 (정직하게)

- **"Celery를 쓰면 처리가 더 빨리 끝난다"는 틀렸습니다.** 모든 보고를 다 처리하는 데 걸린 시간은 Celery 워커 1개(40.4초)와 2개(21.4초)가 오히려 "Celery 없이"(16.8초)보다 길고, 4개(13.9초)에서야 비슷해집니다. 일을 다른 곳으로 옮긴 것이지 일이 빨라진 것이 아닙니다. 이점은 위 2, 3번입니다.
- **워커가 많을수록 접수 응답이 느려졌습니다**(p95 3.7초에서 6.8초). 처리를 하는 워커와 접수를 받는 gunicorn이 같은 PC의 CPU와 DB를 두고 경쟁하기 때문으로 짐작합니다(추정). 실제 서비스에서는 서버를 나누면 이 경쟁이 줄어듭니다.
- **접수 응답 수 초는 "1,000대가 같은 순간에 몰린" 극단적인 상황의 값입니다.** gunicorn 워커 3개가 1,000건을 받는 동안 대부분이 줄을 서 기다린 시간입니다. 평소 흐름(에이전트가 수 초 간격으로 따로 보고)의 응답 시간은 이 표로 알 수 없고, **측정하지 않았습니다.**

## 측정 조건과 한계

- 환경: 한 대의 PC(CPU 22개 논리 코어, 메모리 15.4GB, Docker Desktop). **Locust, Nginx, gunicorn, Celery, PostgreSQL, RabbitMQ를 모두 같은 PC에서** 돌렸습니다. 따라서 절대값은 이 PC에서의 값이며 운영 서버의 성능이 아닙니다. 컨테이너에 CPU 제한은 두지 않았습니다.
- gunicorn 워커는 3개로 고정하고 Celery 워커 수만 바꿨습니다.
- 보고 내용: 설치 소프트웨어 10개, 짝수 번호 PC만 KB 1개 설치. DB의 패치는 4개뿐이라 보고마다 패치 상태 줄이 1개씩 만들어집니다. 실제 PC는 패치가 훨씬 많아 처리 시간이 더 길 수 있습니다. 진행 중인 배포는 없는 상태로 쟀습니다(있으면 보고마다 배포 점검이 더해집니다).
- 측정 전에 200건으로 준비 운동을 했고(기록 안 함), 반복 사이의 차이는 있습니다(예: 워커 16개의 3회 처리량이 114~144건/초). 그래서 중앙값을 썼습니다.
- 시간 측정: 접수 시간은 이 PC의 시계, 처리 시간은 Docker 안의 시계를 썼고 두 시계를 섞어서 계산하지 않았습니다.
- 측정하지 않은 것: 에이전트가 간격을 두고 계속 보고하는 상황, gunicorn 워커 수를 바꾼 비교, 배포가 진행 중일 때의 부하.

## 다시 측정하는 방법

Docker Desktop이 켜져 있어야 합니다. 기존 개발 환경(DB 5432, 큐 5672, 화면 8080)과 겹치지 않게 별도 프로젝트 이름(`mpmbench`)과 포트(18080)로 켭니다.

```
cd loadtest
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python benchmark.py up                                   # 전체를 켜고 PC 1,000대를 만든다
.venv\Scripts\python benchmark.py bench --sync --workers 1 2 4 8 16    # 측정 (--repeat 3이 기본)
.venv\Scripts\python benchmark.py down                                 # 끄고 데이터까지 지운다
```

- `locustfile.py`: 가상 에이전트. `LOAD_MODE=burst`(기본, 에이전트마다 한 번씩)와 `steady`(5~10초 간격으로 계속)가 있습니다.
- `benchmark.py`: compose를 켜고, 워커 수를 바꿔 다시 띄우고, Locust를 실행하고, 워커 로그에서 처리 시간을 읽습니다.
- Celery 워커 수는 `CELERY_CONCURRENCY`, gunicorn 워커 수는 `GUNICORN_WORKERS`, "Celery 없이" 비교용 스위치는 `AGENT_REPORT_SYNC=1`입니다. 이 스위치는 부하 테스트 전용이며 기본은 꺼져 있습니다.
